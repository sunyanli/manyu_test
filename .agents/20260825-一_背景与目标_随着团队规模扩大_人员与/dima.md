## 二、需求深度分析

### 2.1 核心领域模型

```
┌──────────────┐       ┌──────────────────┐
│  Department   │       │    Employee       │
│──────────────│       │──────────────────│
│ id (PK)      │──┐    │ id (PK)           │
│ name         │  │    │ name              │
│ parent_id    │◄─┘    │ employeeNo (UQ)   │
│ level/path   │ 1:N   │ phone (UQ)        │
│ sort_order   │       │ dept_id (FK)      │
│ status       │       │ position          │
│ created_at   │       │ status (在职/离职) │
│ updated_at   │       │ entry_date        │
└──────────────┘       │ resign_date       │
                       │ created_at        │
                       │ updated_at        │
                       └──────────────────┘
                                │
                                │ 1:N
                                ▼
                       ┌──────────────────┐
                       │ TransferRecord   │
                       │──────────────────│
                       │ id (PK)          │
                       │ employee_id (FK) │
                       │ from_dept_id     │
                       │ to_dept_id       │
                       │ from_position    │
                       │ to_position      │
                       │ reason           │
                       │ operator_id      │
                       │ created_at       │
                       └──────────────────┘
```

### 2.2 需求逐项澄清

#### 需求1：部门树形结构

| 维度 | 分析 |
|------|------|
| **树模型** | 邻接表模型（parent_id），适合"懒加载"逐层展开；若需全树一次性查询，可补充物化路径(materialized path) |
| **懒加载** | GET /api/departments/tree?parentId=0 逐层获取；前端首次加载根节点，点击展开时请求子节点 |
| **拖拽** | PUT /api/departments/{id}/move 变更 parent_id；需校验：不能将节点拖到自己子树下（循环引用检测） |
| **未明确点** | 排序规则（是否支持 sort_order 字段）、是否支持多根节点、部门删除/禁用逻辑 |

#### 需求2：员工新增（唯一性校验）

| 维度 | 分析 |
|------|------|
| **唯一性** | 工号(employeeNo) + 手机号(phone) 全局唯一；DB 层唯一索引保底 + 应用层实时校验 |
| **实时校验** | GET /api/employees/check?field=employeeNo&value=... — 前端 blur 事件触发；需注意并发注册时的竞态（唯一索引最终保底） |
| **部门校验** | 提交时校验 deptId 是否存在且为有效部门（非禁用状态） |
| **未明确点** | 手机号格式校验规则、工号生成规则（手动还是自动生成）、是否需邮箱字段 |

#### 需求3：人员调动（级联更新与快照）

| 维度 | 分析 |
|------|------|
| **核心事务** | 更新 dept_id + position；写入调动记录；级联更新审批流 |
| **级联更新** | 审批流节点变更（如"前端主管→后端主管"）——这涉及审批系统的数据，需确认审批系统是否在同一仓库、是否通过 API 回调还是直接操作 DB |
| **留痕** | TransferRecord 表独立记录；包含操作人、时间、原因 |
| **未明确点** | 审批流级联更新的具体范围（仅更新默认审批人 or 所有进行中的审批单？）、调动是否需要审批流程本身？ |

#### 需求4：员工离职（逻辑删除与状态隔离）

| 维度 | 分析 |
|------|------|
| **逻辑删除** | status 字段标记"离职"，保留数据行 |
| **资源释放** | 系统账号许可释放、登录权限清除——需确认这些系统是否在本模块范围内 |
| **历史保留** | 考勤/审批历史保留，查询时带状态标识 |
| **未明确点** | 离职日期与生效时间的关系（定时生效 or 立即生效）、离职后是否可复职、复职流程 |

## 三、技术架构建议

### 3.1 技术选型（✅ 已确认）

| 层面 | 选定方案 | 说明 |
|------|---------|------|
| 后端框架 | **Python FastAPI** | 异步高性能，Pydantic 类型校验，自动生成 OpenAPI 文档 |
| 数据库 | **MySQL** | 关系型，支持递归 CTE（MySQL 8.0+） |
| ORM | SQLAlchemy (async) + Alembic | FastAPI 生态首选，支持异步与迁移 |
| 缓存 | Redis（可选） | 部门树缓存（读多写少场景） |
| 审批系统 | **独立服务 + API 回调** | 调动时通过 HTTP 通知审批系统更新节点 |
| 权限系统 | **本模块内置** | 角色枚举（超管/HR/部门主管），接口级鉴权中间件 |

### 3.2 API 契约汇总

| 方法 | 路径 | 用途 | 状态 |
|------|------|------|------|
| GET | /api/departments/tree | 获取部门树（懒加载） | 已定义 |
| PUT | /api/departments/{id}/move | 拖拽调整父部门 | 已定义 |
| GET | /api/employees/check | 实时唯一性校验 | 已定义 |
| POST | /api/employees | 新增员工 | 已定义 |
| POST | /api/employees/{id}/transfer | 人员调动 | 已定义 |
| PUT | /api/employees/{id}/resign | 办理离职 | 已定义 |

**缺失的 API（建议补充）**：
- `GET /api/departments` — 部门列表（非树形）
- `POST /api/departments` — 新增部门
- `PUT /api/departments/{id}` — 编辑部门
- `DELETE /api/departments/{id}` — 删除部门（需校验无子部门、无员工）
- `GET /api/employees` — 员工列表（分页、按部门/状态筛选）
- `GET /api/employees/{id}` — 员工详情
- `PUT /api/employees/{id}` — 编辑员工信息
- `GET /api/employees/{id}/transfers` — 调动记录查询

### 3.3 仓间对齐点

当前两仓无代码依赖，后续对齐点：
1. **接口契约**：`manyu_test` 作为 API 提供方需定义 OpenAPI/Swagger 文档，`manyu_test1` 消费时按契约对接
2. **数据格式**：统一响应体 `{ code, data, msg }` 格式
3. **错误码**：跨仓统一错误码枚举

## 四、待决策问题（需用户澄清）

以下问题按优先级排列，影响后续设计与实现：

### 高优先级（✅ 已确认）

1. ✅ **技术栈选择** → **Python FastAPI** + SQLAlchemy (async) + Alembic
2. ✅ **数据库选型** → **MySQL**（8.0+，支持递归 CTE）
3. ✅ **审批系统对接方式** → **独立服务 + API 回调**（调动时 HTTP 通知）
4. ✅ **权限系统** → **本模块内置**（超管/HR/部门主管 角色枚举 + 中间件鉴权）

### 中优先级（影响功能细节）

5. **工号生成规则**：手动输入还是系统自动生成？自动生成的格式（如 EMP-20230001）？
6. **部门树深度限制**：是否限制最大层级深度？
7. **离职后复职**：是否支持？复职时原部门/职位是否保留？
8. **资源释放范围**：离职时"系统账号许可"和"登录权限"——这些系统的接口是什么？
9. **员工跨部门兼岗**：是否支持一个员工属于多个部门？（当前设计为 N:1）
10. **批量操作**：是否支持批量导入员工、批量调动？

### 低优先级（影响体验细节）

11. **部门排序**：拖拽之外是否支持手动排序号？
12. **历史数据审计**：部门变更、员工信息变更是否需要审计日志？
13. **国际化**：是否需要 i18n？
